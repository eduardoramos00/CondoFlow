### What was built
Full project scaffold: Next.js 16 App Router with the `src/` directory layout, TypeScript in strict mode, Tailwind CSS v4 with a CSS-first theme, shadcn/ui wired with the base-nova style, Inter font, and all runtime dependencies installed.

### Technical decisions
- **Next.js App Router over Pages Router:** All server-side logic lives in Server Components and Server Actions. No `getServerSideProps` / `getStaticProps` patterns — the App Router's async component model and `"use server"` directives are a better fit for a data-heavy SaaS with fine-grained auth.
- **`src/` directory layout:** Groups all application source under one root, making it trivially easy to distinguish application code from config files at the repo root.
- **Tailwind CSS v4 with `@theme` CSS-first config:** v4 replaced `tailwind.config.js` with `@theme { }` blocks inside the global CSS file. Design tokens (`--font-inter`, chart colours, sidebar colours) are declared as CSS custom properties under `@theme inline`, ensuring they propagate to both Tailwind utility classes and any CSS-variable consumers.
- **`@custom-variant dark (&:is(.dark *));`:** Registers the `dark:` variant to activate when an ancestor element has the `dark` class — the standard Tailwind v4 pattern for class-based dark mode. The `dark` class is applied permanently on `<html>` (dark-mode-first design).
- **shadcn/ui base-nova style over the default style:** Uses `@base-ui/react` as the primitive layer instead of Radix UI. Base UI is the MUI team's newer unstyled primitive library; it has a slightly different API (`render` prop instead of `asChild`) but the same accessibility guarantees. Chosen because it was pre-configured in the shadcn base-nova template used at bootstrap time.
- **`title.template: "%s — CondoFlow"` in root metadata:** Every page that exports a `title` string from its `export const metadata` gets the suffix automatically — no per-page boilerplate for the brand suffix.
- **`.env.local.example` committed to the repo:** Documents every required variable with descriptive comments. Prevents "works on my machine" issues when onboarding contributors. The real `.env.local` is gitignored.

### Security / invariants enforced
- `strictNullChecks`, `noImplicitAny`, and `exactOptionalPropertyTypes` enabled in `tsconfig.json` — TypeScript cannot be weakened without changing the config file explicitly.
- `SUPABASE_SERVICE_ROLE_KEY` is listed in `.env.local.example` but never hardcoded anywhere in the codebase.

### Known limitations / deferred work
- `src/lib/supabase/types.ts` is a hand-written stub (`Record<string, Json>` for all tables). It must be replaced with `npx supabase gen types` output after migrations are applied to a live project.
- Light-mode theme tokens exist in `globals.css` (generated by shadcn) but are never applied — the app is permanently in dark mode.

## [Phase 0.2] — Supabase Project Setup
**Date:** 2026-06-09
**Files:**
- `src/lib/supabase/server.ts` (created)
- `src/lib/supabase/client.ts` (created)
- `src/lib/supabase/types.ts` (created — stub)
- `src/lib/auth/session.ts` (created)
- `supabase/config.toml` (created)
- `supabase/seed.sql` (created)
- `src/middleware.ts` (created — session-refresh stub)

### What was built
Supabase client layer: two server-side factory functions (`createServerSessionClient` for RLS-respecting queries, `createServerSupabaseClient` for service-role bypasses), one browser-side factory (`createBrowserSupabaseClient` for Realtime only), and three session helpers (`getServerSession`, `getServerUser`, `getServerUserId`). Storage bucket provisioning and local dev config included.

### Technical decisions
- **Two server clients, one browser client:** The server-session client uses the anon key + request cookies, fully respects RLS, and is used for all user-scoped reads. The service-role client bypasses RLS entirely and is used only in server actions that need privileged access (e.g. trigger-like inserts, cross-tenant admin ops). The browser client uses the anon key for Realtime subscriptions only — it has no write access to any table.
- **`createServerSessionClient` is `async`:** Next.js 15+ requires `await cookies()` (the `cookies()` API returns a Promise). The async factory handles this transparently — all callers just `await createServerSessionClient()`.
- **`requireEnv()` throws at call time:** Server startup fails immediately with a clear error message if a required env var is missing, rather than failing silently at first use. This surfaces misconfiguration during `npm run dev` rather than during a production request.
- **`getServerUser()` makes a network call to Supabase Auth:** Unlike `getServerSession()` (which reads from the signed cookie), `getServerUser()` validates the JWT against the Supabase Auth server. For mutations and sensitive reads, this prevents token reuse after revocation. The docstring explicitly documents when to use each.
- **`createBrowserSupabaseClient` throws on missing env vars:** Browser clients are instantiated lazily (not at module load time), so the guard must be inside the factory function. It throws with a descriptive message pointing to `.env.local.example`.
- **Storage buckets provisioned in `supabase/seed.sql`:** `invoices` and `incident-media` buckets are created with `is_public = false` and RLS policies in the seed file rather than hardcoded SQL in a migration. This separates environment-specific provisioning (seed) from schema history (migrations).

### Security / invariants enforced
- `import "server-only"` at the top of `server.ts` — Next.js throws a build error if this module is accidentally imported by a client component.
- `import "server-only"` at the top of `session.ts` — same protection for the session helpers.
- Service role client created with `autoRefreshToken: false, persistSession: false` — it is a stateless admin client, never tied to a user session.
- Middleware uses `supabase.auth.getUser()` (server-validates JWT) for the session check — not `getSession()` (reads cookie without network validation).

### Known limitations / deferred work
- Storage bucket RLS policies in `seed.sql` are placeholders; the real policies (scoped by `building_id`) require the `buildings` and `unit_ownership` tables from Phases 1.1–1.2 to be applied first.
- Supabase Auth email templates (confirmation, recovery) use Supabase default wording — custom PT-PT templates are deferred to Phase 4.

## [Phase 0.3] — App Shell & Route Groups
**Date:** 2026-06-09

### What was built
Three Next.js route groups with their layouts, the full provider composition chain (UserProvider → NotificationProvider), and stub versions of Sidebar and TopNav. The `UserContext` wires `onAuthStateChange` for reactive user state. `NotificationContext` establishes a Supabase Realtime subscription scoped to the authenticated user.

### Technical decisions
- **Route groups `(auth)`, `(dashboard)`, `(marketing)`:** Next.js route groups (parentheses syntax) create layout boundaries without adding path segments to the URL. Auth pages (`/login`, `/register`) share a centred-card layout; dashboard pages share the full-height shell layout; marketing pages get a minimal wrapper. Each group can have its own `loading.tsx`, `error.tsx`, and `not-found.tsx` without interference.
- **`(dashboard)/layout.tsx` uses `overflow-hidden` on the root + `overflow-y-auto` only on `<main>`:** This is the standard fixed-sidebar / scrollable-content pattern. The outer `h-screen overflow-hidden` clips the viewport; the inner `flex-1 overflow-y-auto` creates the single scroll container for page content. Without `min-w-0` on the content column, wide content can cause the sidebar to shrink — `min-w-0` fixes this.
- **`UserContext` uses `onAuthStateChange` not `getUser()`:** `onAuthStateChange` fires immediately with the current session on mount and then reactively on sign-in/sign-out events. A separate `getUser()` call on mount would require two state updates (loading → loaded) and an extra network round-trip. The single listener handles both the initial state and subsequent changes.
- **`NotificationContext` uses Supabase Realtime `postgres_changes`:** The `INSERT` filter `recipient_user_id=eq.${user.id}` means the subscription only fires for events destined for the current user. The channel is named `notifications:${user.id}` so multiple browser tabs for the same user share the same channel without duplication. The channel is cleaned up on unmount (`removeChannel`).
- **`NotificationProvider` nested inside `UserProvider`:** `NotificationContext` calls `useUser()` to get the user ID for the Realtime filter. It must be a descendant of `UserProvider` in the tree.
- **Sidebar and TopNav delivered as stubs:** Phase 0.3 established the layout contract (the shell renders and compiles) without implementing the dynamic features (building selector, role-based nav, live notifications). The stubs were upgraded to full implementations in Phase 1.5.
- **`AppNotification` type mirrors the `notifications` table schema:** Defined in `NotificationContext.tsx` as a hand-maintained type (not generated from the DB). When `supabase gen types` is run after Migration 005 (Phase 4), this type should be replaced with the generated one and the manual definition removed.

### Security / invariants enforced
- `NotificationContext` clears all notifications and unsubscribes when `user` becomes `null` (sign-out) — no notification data leaks between sessions on the same browser tab.
- The Realtime subscription filter uses `recipient_user_id=eq.${user.id}` — Supabase enforces this filter server-side; a malicious client cannot receive another user's notifications by manipulating the subscription.

### Known limitations / deferred work
- `NotificationContext` only handles `INSERT` events — `UPDATE` (e.g. delivery_status changes from a background job) is not subscribed to. Full bidirectional sync is deferred to Phase 4.
- `AppNotification.payload` is typed as `Record<string, unknown>` — the per-event-type payload shape is untyped until Phase 4 defines all event types.
- Sidebar and TopNav were stubs with disabled buttons. Fully implemented in Phase 1.5.

## [Phase 1.1] — Database: Core Schema
**Date:** 2026-06-09
**Files:**
- `supabase/migrations/20260609000001_core_schema.sql` (created)

### What was built
PostgreSQL migration establishing the multi-tenant foundation: `profiles` (extends `auth.users`), `buildings` (one row per condominium), and `user_building_roles` (the assignment bridge between users and buildings). Row-Level Security enabled on all three tables with five RLS policies and two SECURITY DEFINER triggers.

### Technical decisions
- **Composite PK on `(user_id, building_id)` in `user_building_roles`:** Prevents a user from holding two roles in the same building at the DB level — no application-layer deduplication needed.
- **ENUM for `role` column:** `'GESTOR' | 'CONDÓMINO'` enforced as a PostgreSQL text check rather than a separate lookup table — simpler queries, no join overhead for the most frequent access pattern.
- **`handle_new_user()` trigger (SECURITY DEFINER):** Auto-creates a `profiles` row from `raw_user_meta_data->>'full_name'` on every Supabase Auth sign-up. Removes the need for a post-sign-up server action and prevents orphaned auth users with no profile.
- **`handle_new_building()` trigger (SECURITY DEFINER):** Auto-inserts `(owner_gestor_id, new_building_id, 'GESTOR')` into `user_building_roles` when a building is created. Without this, the GESTOR's own `buildings_gestor_select` RLS policy would never match their new building — it would be invisible immediately after creation.
- **ASCII-only policy names:** Policy `buildings_condomino_select_own` uses unaccented ASCII identifiers to avoid `pg_dump` / CI encoding corruption on non-UTF-8 environments.
- **`UNIQUE (fiscal_number)` on buildings:** Portuguese NIF (tax number) must be unique per legal entity. DB constraint prevents duplicate condominium registrations at the source.
- **`profiles_building_member_select` policy:** Allows a GESTOR to read profiles of all condóminos in their buildings via a JOIN through `user_building_roles`. Without it, the GESTOR cannot display resident names or avatars anywhere in the UI.

### Security / invariants enforced
- RLS enabled (`FORCE ROW LEVEL SECURITY`) on all three tables — service role bypasses RLS only where explicitly needed.
- All policies follow the `{table}_{role}_{action}` naming convention.
- `ON CONFLICT DO NOTHING` in `handle_new_building()` prevents trigger re-runs from inserting duplicate role rows.

### Known limitations / deferred work
- `avatar_url` column on `profiles` is nullable; avatar upload flow is deferred to Phase 9.
- `user_building_roles` has no `status` column — suspension/deactivation of a user within a building is deferred to Phase 8.2 (`suspend_user` action).

## [Phase 1.2] — Database: Unit & Ownership Schema
**Date:** 2026-06-09
**Files:**
- `supabase/migrations/20260609000002_units_schema.sql` (created)

### What was built
Migration adding `units` (individual fractions within a building with their permilagem share) and `unit_ownership` (historical ownership log with start/end dates). Includes a database trigger enforcing the Portuguese legal constraint that the sum of all permilagem values within a building must never exceed 10 000.

### Technical decisions
- **Permilagem stored as `INT` (0–10000):** Portuguese law (DL 268/94) defines fractions in thousandths (per mille). Storing as integer avoids floating-point imprecision. Value 850 represents 8.50‰. Display formatting (→ "8,50‰") is handled in application layer via `formatPermilagem()`.
- **`check_permilagem_sum()` trigger fires `BEFORE INSERT OR UPDATE OF permilagem, building_id`:** Only fires when the relevant columns change, avoiding unnecessary recalculation on unrelated UPDATE operations.
- **`id != NEW.id` exclusion in trigger sum query:** Works uniformly for both INSERT (the new row's UUID is not yet committed, so the condition is always true — correct exclusion) and UPDATE (excludes the current row to avoid double-counting its old value).
- **`SECURITY DEFINER` + `SET search_path = public` on trigger function:** Without SECURITY DEFINER, the trigger runs under the calling user's RLS context. If RLS ever filters out some units for the caller, the trigger reads a falsely-low sum and silently permits a total exceeding 10 000.
- **`PERFORM … FOR UPDATE` lock on parent building row:** Serializes concurrent INSERT operations per building. Without this, two simultaneous INSERTs can both pass the BEFORE trigger (both read the pre-commit sum), both commit, and the actual sum exceeds 10 000.
- **Partial unique index `idx_unit_ownership_one_active_owner ON unit_ownership (unit_id) WHERE ended_at IS NULL`:** Guarantees at most one active owner per unit at any time without preventing historical ownership records.
- **`CHECK (ended_at > started_at)` on `unit_ownership`:** Prevents logically invalid ownership periods at the DB level.
- **`ERRCODE = 'check_violation'`** on trigger exception: Allows application layer to catch and display a user-friendly "permilagem total would exceed 10 000" message by testing the SQLSTATE code.

### Security / invariants enforced
- Permilagem integrity enforced at DB level (not just application code) — cannot be bypassed by direct DB access or bulk imports.
- `units_condómino_select_own` policy restricts condóminos to only their assigned units via `unit_ownership` join — they cannot enumerate all units in their building.
- `unit_ownership_gestor_all` WITH CHECK uses unqualified `unit_id` to avoid column reference ambiguity in complex query plans.

### Known limitations / deferred work
- `unit_ownership` insert (assigning a condómino to a unit) is done by GESTOR via Phase 1.2 schema; the UI for this assignment is deferred to Phase 2.
- The trigger validates sum ≤ 10 000 but does not enforce sum = 10 000 — a building can exist with partial allocation. Full allocation validation is a business rule checked in the budget generation flow (Phase 2.5).

### What was built
Complete authentication flow: four UI pages with react-hook-form + Zod validation, five server actions (signIn, signUp, signOut, forgotPassword, resetPassword), an OAuth/magic-link callback route handler, and global middleware for route protection and auth-route bypassing.

### Technical decisions
- **Server-side Zod validation in server actions:** Server actions are callable directly via `fetch()` from any client, bypassing all browser-side Zod schemas. Each action re-validates with the same schema before processing. `passwordSchema` includes `max(72)` matching the bcrypt input limit.
- **`resolveRoleRedirect()` in signIn — not in middleware:** A DB query on every request via middleware would be prohibitively expensive. Role-based redirect runs once at sign-in and stores the destination. Middleware only checks session presence, not role.
- **`/reset-password` excluded from `AUTH_PREFIXES`:** The password reset flow requires an authenticated session (established by `/auth/callback` exchanging the recovery code). Including it in AUTH_PREFIXES would redirect authenticated users away from the reset form immediately after clicking their recovery email link — permanently breaking the flow.
- **Open redirect prevention in `/auth/callback`:** `new URL(next, origin)` ignores `origin` when `next` is an absolute URL. Fix: `const next = rawNext.startsWith("/") && !rawNext.startsWith("//") ? rawNext : "/dashboard"` validates the parameter as a strict relative path before use.
- **Silent error swallowing in `forgotPassword`:** Returning an error for non-existent emails reveals whether an address is registered (email enumeration). Only rate-limit errors are surfaced; all others silently return as if the email was sent.
- **`data: { full_name: fullName }` in `signUp`:** Populates `raw_user_meta_data` which the `handle_new_user()` DB trigger reads to auto-create the `profiles` row. No second DB round-trip needed after sign-up.
- **`redirectTo` preserves path in middleware redirect:** `loginUrl.searchParams.set("redirectTo", pathname)` allows future phases to send the user to their intended destination after login instead of always defaulting to `/dashboard`.

### Security / invariants enforced
- Every protected action begins with `getServerSession()` — no action proceeds without a valid session.
- `signOut` includes a session guard before calling Supabase `signOut()` — prevents unauthenticated invocations from triggering server-side operations.
- `resetPassword` re-validates the session before calling `updateUser()` — the recovery link could be expired.

### Known limitations / deferred work
- The `redirectTo` param from middleware is read by middleware itself but not yet consumed by `signIn` to redirect back to the original path — wired in Phase 1.4+.
- Email confirmation flow (Supabase email verification) is configured in Supabase dashboard; the UI shows the "Email not confirmed" error string but has no dedicated confirmation page yet.

## [Phase 1.4] — RBAC Utilities
**Date:** 2026-06-09
**Files:**
- `src/lib/auth/can.ts` (created)
- `src/lib/auth/roles.ts` (created)

### What was built
Two-module RBAC system: a client-safe permission matrix (`can.ts`) and a server-only role enforcement layer (`roles.ts`). Together they cover 48 named actions across all platform domains, with full SUPERADMIN bypass and typed `UnauthorizedError` for structured error handling in server actions.

### Technical decisions
- **Split into two modules (`can.ts` / `roles.ts`):** `can.ts` has no server-only imports and is safe to bundle into client components (e.g. `<TransitionButton>` which must hide controls the user cannot act on). `roles.ts` has `import "server-only"` and is never bundled to the browser — it holds the DB call (`getUserRole`) and the `UnauthorizedError` class.
- **`ReadonlySet<Action>` for permission sets:** Immutable at module load time — no accidental mutation, fast `O(1)` `.has()` lookup, and TypeScript enforces that all set entries satisfy the `Action` union type.
- **`SUPERADMIN` bypass in `can()` returns `true` for all 48 actions:** SuperAdmin is a platform role stored in `app_metadata`, not a building role. Checking `app_metadata` on the client is acceptable since it is JWT-signed and cannot be self-modified by the user.
- **`getUserRole` uses the service-role client:** Bypasses RLS so server actions can check a user's building role regardless of the calling context. Returns `null` on error (fail-closed — no accidental grants on DB failure).
- **`requireRole` throws `UnauthorizedError`, not returns `{ error }`:** Server actions can catch it with `instanceof UnauthorizedError` and convert it to a structured response. Throwing prevents accidental "forget to check the return value" bugs.
- **`Object.setPrototypeOf` in `UnauthorizedError`:** TypeScript compiles `class extends Error` to ES5 prototype chains. Without this fix, `err instanceof UnauthorizedError` returns `false` at runtime in transpiled output targeting ES5/ES2015.
- **Empty `allowedRoles` guard in `requireRole`:** `allowedRoles.join(" ou ")` on an empty array produces `""`. Guard: `allowedRoles.length ? allowedRoles.join(" ou ") : "adequado"` prevents a blank role name in the error message without changing security behavior (empty array still always throws).

### Security / invariants enforced
- `report_incident` is CONDÓMINO-only per spec — GESTORs assess and dispatch but do not create incidents.
- `grant_proxy` is CONDÓMINO-only — residents delegate their own assembly vote; a GESTOR cannot proxy-vote on behalf of a resident.
- All 6 SuperAdmin-only actions (`list_all_buildings`, `list_all_users`, `assign_gestor_to_building`, `revoke_gestor`, `suspend_user`, `process_data_deletion`) are absent from all building-role sets — no privilege escalation path from GESTOR.
- Zero orphaned actions — all 48 entries in the `Action` union are assigned to at least one role or are intentionally SuperAdmin-only.

### Known limitations / deferred work
- No TypeScript exhaustiveness check that forces every new `Action` to be added to a permission set. A Python audit script (`comm -23` on extracted sets) was used to verify completeness during the review.
- `getUserRole` uses two sequential DB round-trips in the stub-typed client. Once `supabase gen types` is run against the real schema, this can be replaced with a single join query.

### Technical decisions
- **`BuildingContext` with `localStorage` persistence:** The selected building must survive page navigations without re-fetching. `localStorage` (key: `condoflow:selected_building_id`) persists the last selection across browser sessions. On load, the saved ID is validated against the live buildings list — if the building no longer exists (e.g. user was removed), it falls back to `list[0]`.

- **`getUserBuildings()` returns `userRole` per building:** Avoids a separate `getUserRole()` call in the Sidebar on every render. The role travels with the building record, and the Sidebar derives `effectiveRole` from `selectedBuilding.userRole` with zero extra DB round-trips.
- **Role-filtered nav via `can('view_suppliers', role)` not a role string comparison:** Decouples the nav filter from hardcoded role names. If a future role is added to the permission matrix, the nav updates automatically — no changes to Sidebar needed.
- **`isItemVisible()` checks `superAdminOnly` first before the `!role` guard:** Ensures SuperAdmin-exclusive items are hidden when no role is loaded, not just when the role is a building role.
- **`<DropdownMenu>` and `<Popover>` from shadcn/base-nova:** Project uses `@base-ui/react` (not Radix UI) as the primitive layer under shadcn's base-nova style. The API differs slightly (`render` prop instead of `asChild`), but the shadcn wrappers abstract this. No hand-rolled overlay primitives.
- **`SkeletonTable` cols constrained to `2 | 3 | 4 | 5 | 6` union:** Avoids inline `style={{ gridTemplateColumns }}` (banned by no-inline-styles rule). A `Record<TableCols, string>` lookup maps each value to a Tailwind `grid-cols-N` class that is statically present in the CSS output.
- **`StatusBadge` as the single source of truth for status colors:** All entity status strings (quota, expense, assembly, incident, budget, role) resolve their pill color through one component. Prevents color drift where the same status renders differently on different pages.
- **`BuildingProvider` positioned after `NotificationProvider` in the provider chain:** Both depend on `useUser()`. Ordering doesn't affect function but placing `BuildingProvider` last keeps it closest to the consuming components and makes the dependency chain readable top-to-bottom.
- **Promise `.catch().finally()` in `BuildingContext`:** `void promise.then(...)` without a catch silently leaves `isLoading: true` on network failure — the Sidebar renders a permanent skeleton. `.catch(() => {}).finally(() => setIsLoading(false))` ensures the skeleton always resolves.

### Security / invariants enforced
- `getUserBuildings()` session-guarded — returns `[]` for unauthenticated calls.
- Service role client used in server action — never exposes the anon key to building queries.
- `effectiveRole` derived server-side from `selectedBuilding.userRole` (set by the server action) — the client cannot inject a different role by modifying state.
- `isSuperAdmin` check uses `user.app_metadata['role']` (JWT-signed, read-only by users) not `user_metadata`.

### Known limitations / deferred work
- Breadcrumb `SEGMENT_LABELS` only covers static route segments. Dynamic segments (UUIDs, slugs on detail pages) render as raw strings. Dynamic label resolution is deferred to the pages that introduce those routes (Phase 2+).
- Search button renders but performs no action — full search is deferred to a later phase.
- Building selector shows "Sem edifícios" for SuperAdmin (who has no `user_building_roles` entries). The Platform admin section under Administração is their entry point instead. A SuperAdmin-specific building browser is planned for Phase 8.2.

## [Phase 2.1] — Database: Financial Schema
**Date:** 2026-06-09
**Files:**
- `supabase/migrations/20260609000003_financial_schema.sql` (created)
- `TODO.md` (subphase 2.1 marked `[x]`)

### What was built
Full financial ledger schema: three new enum types (`budget_status_enum`, `budget_category_enum`, `quota_status_enum`), five new tables (`budgets`, `budget_line_items`, `quotas`, `payments`, `audit_log`), a BEFORE trigger enforcing quota lifecycle transitions, covering indexes for common query paths, RLS enabled on all five tables with nine policies, and an append-only `audit_log` design (no UPDATE or DELETE policies created).

### Technical decisions
- **All monetary columns typed as `INT` (euro cents), never `FLOAT`/`DECIMAL`:** Floating-point arithmetic on money produces rounding errors that accumulate across quota generation runs. Integer arithmetic for cents is lossless and exactly reproducible. Matches the Architect invariant: "Currency precision rule — all monetary values in the database are integers representing euro cents. No FLOAT or DECIMAL columns for money. Ever."
- **`budget_category_enum` shared between `budget_line_items` and Phase 3 `expenses`:** Defined once in this migration so that when the expenses table is created in 004, it imports the same enum. This enforces reporting consistency: budget-vs-expense variance queries join on the same category keys without casting.
- **`budgets_building_year_unique` UNIQUE constraint:** Prevents two budget records for the same building and fiscal year. Without this, the quota generation action (Phase 2.5) could accidentally generate duplicate quotas from two active budgets for the same year.
- **`quotas_unit_due_date_unique` UNIQUE constraint:** Idempotency guard for the bulk `generateMonthlyQuotas` server action. Re-running it for the same month on the same building either silently no-ops (ON CONFLICT) or raises a unique violation — prevents double billing.
- **`quotas_paid_at_consistency` CHECK constraint:** `paid_at` must be non-null when `status = 'PAID'` and null otherwise. Enforces at the DB level what application code sets during `markQuotaPaid` — prevents orphaned timestamps and NULL-check bugs in reporting queries.
- **`check_quota_status_transition` BEFORE trigger:** Enforces `PENDING → {PAID, OVERDUE, WAIVED}` and `OVERDUE → {PAID, WAIVED}` lifecycle. PAID and WAIVED are terminal states. Implemented as a trigger rather than a CHECK constraint because transition validation depends on the OLD row value, which is not accessible in a static CHECK.
- **`building_id` added to `audit_log` (not in the minimum spec column list):** Without a `building_id` anchor, a per-building RLS SELECT policy on `audit_log` would require dynamic joins across every financial table via `(target_table, target_id)` — not expressible as a static `USING` expression in PostgreSQL RLS. Adding `building_id` makes the policy trivially correct and the table useful for the Phase 2.4 audit viewer UI.
- **`ON DELETE SET NULL` for `audit_log` FKs (`actor_user_id`, `building_id`):** Audit history must survive the deletion of the actor account or the building. `SET NULL` preserves the event record while clearing the FK reference. `CASCADE` would silently destroy audit evidence on account deletion, which violates the GDPR anonymisation requirement (Phase 9 must anonymise, not delete).
- **`payments` uses `ON DELETE RESTRICT` for both FKs:** A payment record is financial evidence. Deleting the referenced quota or profile is refused at the DB level. The only valid path to remove ownership of a payment is the GDPR anonymisation flow (Phase 9).
- **No RLS `UPDATE` or `DELETE` on `audit_log` — combined with `BEFORE` triggers for true append-only enforcement:** For `authenticated` session-key clients, omitting UPDATE/DELETE policies is sufficient (no matching policy → operation denied). However, Supabase's `service_role` Postgres role carries `BYPASSRLS` and would bypass that omission entirely. The append-only invariant is therefore enforced by `BEFORE UPDATE` and `BEFORE DELETE` triggers (`prevent_audit_log_mutation`), which raise `insufficient_privilege` unconditionally regardless of the caller's Postgres role. See Post-review fix C-1.
- **`audit_log_self_insert` scoped to the caller's buildings with actor binding:** Fallback for server actions using the session-key client. The `WITH CHECK` ensures the authenticated user can only name themselves as `actor_user_id` (or NULL for system events) and cannot insert entries for buildings they have no role in. Service-role writes (the primary path) bypass RLS but remain subject to the append-only triggers. See Post-review fix C-2 and M-1.

### Security / invariants enforced
- RLS enabled on all five tables — no table ships without policies.
- Quota lifecycle: PAID and WAIVED are terminal states; no backwards transitions to PENDING enforced at the trigger level.
- `audit_log` is append-only by design (no UPDATE/DELETE policies); records survive actor account deletion via `ON DELETE SET NULL`.
- All monetary constraint checks (`CHECK (amount_cents > 0)`, `CHECK (reserve_amount_cents >= 0)`, `CHECK (reserve_amount_cents <= total_amount_cents)`) reject bad data at the DB layer regardless of application-level validation.
- `budget_line_items_condomino_select_own` and `budgets_condomino_select_own` policies: Condóminos have read-only visibility into building budget data (transparency mandate per Portuguese condominium law) with no INSERT/UPDATE/DELETE access.

### Post-review fixes (Reviewer pass — same date)
Two critical and three minor issues found and resolved before the migration was finalised:

- **C-1 — `audit_log` append-only not enforced at DB level:** `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` only blocks non-BYPASSRLS roles. Supabase's `service_role` Postgres role carries `BYPASSRLS`, meaning every server action using `createServerSupabaseClient()` could silently mutate audit records. Fixed by adding `prevent_audit_log_mutation()` trigger function + `BEFORE UPDATE` and `BEFORE DELETE` triggers on `audit_log`. Triggers fire before the statement executes and cannot be bypassed by any Postgres role — they are the only true DB-level enforcement of the append-only invariant.
- **C-2 — `audit_log_authenticated_insert` allowed `actor_user_id` forgery:** The original `WITH CHECK` only validated `building_id` membership. An authenticated caller could insert a row with `actor_user_id = <any other user's UUID>`, forging audit entries. Fixed by adding `(actor_user_id = auth.uid() OR actor_user_id IS NULL)` to the `WITH CHECK` expression.
- **M-1 — Policy `audit_log_authenticated_insert` broke naming convention:** Renamed to `audit_log_self_insert` to restore the `{table}_{role}_{action}` pattern used throughout all migrations.
- **M-2 — `budgets_gestor_all` `WITH CHECK` did not enforce `created_by = auth.uid()`:** A GESTOR could forge the creator attribution on INSERT. Fixed by adding `AND (created_by = auth.uid())` to the `WITH CHECK` expression.
- **M-3 — `audit_log_gestor_select` NULL-`building_id` behaviour undocumented:** Rows with `building_id IS NULL` (system/cron events) are invisible to session-key clients because SQL `NULL = value` is never true in EXISTS subqueries. Documented in a SQL comment on the policy; these entries are intentionally accessible only via the service-role client in the Phase 8 SuperAdmin portal.

### Known limitations / deferred work
- The 10% reserve fund minimum (Artigo 4.º, Decreto-Lei n.º 268/94) is not enforced at the DB level — a `CHECK (reserve_amount_cents >= total_amount_cents * 0.10)` would be the correct constraint, but the spec calls for a Gestor UI warning (Phase 2.4) rather than a hard rejection, so it is left to application logic.
- `audit_log_gestor_select` allows a GESTOR to SELECT all audit entries for any of their buildings — there is no further per-action or per-table filter at the policy level. Phase 8 (SuperAdmin) may narrow this if cross-building audit access is introduced.
- `payments.payment_method VARCHAR(50)` is free-form. A `payment_method_enum` ('MB_WAY', 'TRANSFERENCIA', 'NUMERARIO', 'CHEQUE') could tighten the schema but is deferred until Phase 2.5 defines the accepted methods from the UI.
- System-triggered audit log entries (`building_id IS NULL`) are invisible to GESTORs querying via the session-key client. SuperAdmin (Phase 8) reads these via service-role client.

**Date:** 2026-06-09
**Files:**

### What was built
Four pure functions forming the core financial calculation engine, plus a 38-test suite covering exact arithmetic, all rounding branches, display formatting, and permilagem validation. Vitest was installed and configured as the project test runner.

### Technical decisions
- **All arithmetic via `Math.round(a * b / 10_000)` — no `decimal.js`:** Both `calculateUnitQuota` and `calculateReserve` use the same formula: `ROUND(amount_cents × permilagem / 10_000)`. Pure integer inputs and `Math.round` produce integer outputs. The largest intermediate value for a €10 000 000 budget (10^9 cents) × 10 000 permilagem = 10^13, well below `Number.MAX_SAFE_INTEGER` (≈9×10^15). `decimal.js` is therefore unnecessary here and reserved for display-only decimal conversions (Phase 2.3).
- **`calculateReserve` has the same signature and formula as `calculateUnitQuota`:** The semantic difference lives in what the caller passes — `reserveAmountCents` vs `totalBudgetCents`. Two named functions provide clear intent at the call site (Phase 2.4 server actions) without any hidden logic difference.
- **`formatPermilagem` uses `Intl.NumberFormat('pt-PT', …)` for display:** Permilagem is stored out of 10 000; dividing by 100 yields a two-decimal display value. The `pt-PT` locale produces comma as the decimal separator (`"8,50‰"`), matching the Portuguese product requirement. This is a display-only operation — the `value / 100` division here is never stored or used in financial arithmetic.
- **`validateBuildingPermilagem` returns `false` for an empty array:** An empty unit list has a sum of 0, which does not equal 10 000. The guard is explicit rather than relying on the reduce identity to produce 0, because a building with no units is always a configuration error regardless of the sum.
- **Vitest over Jest:** Vitest requires zero transpilation config for ESM/TypeScript and resolves `@/` path aliases natively via `resolve.alias`. Jest requires `ts-jest` or Babel and additional `moduleNameMapper` config for the alias. Vitest runs in under 700 ms including cold start.
- **`vitest.config.ts` wires the `@/*` alias independently of Next.js:** The tsconfig uses `"moduleResolution": "bundler"` which is Next.js-specific and not understood by Vitest's Vite core. The alias is re-declared in `vitest.config.ts` so test imports using `@/` resolve correctly without needing `vite-tsconfig-paths`.

### Security / invariants enforced
- No floating-point arithmetic in any financial calculation path — all functions return integers or display strings only.
- `validateBuildingPermilagem` mirrors the DB-level `check_permilagem_sum` trigger from migration 002, providing a fast synchronous pre-check at the application layer before any DB write is attempted.
- Pure functions with no side effects — no database calls, no environment reads, no mutation of arguments.

### Known limitations / deferred work
- Rounding remainder distribution (assigning leftover cents to the highest-permilagem unit) is intentionally deferred to `generateMonthlyQuotas` in Phase 2.5, where all unit quotas are computed together and the remainder can be identified and assigned in a single pass.
- `formatPermilagem` uses `Intl.NumberFormat` directly (not the `formatCurrency` utility from Phase 2.3) because permilagem is not a currency value — it is a dimensionless ownership fraction. The reviewer rule banning `Intl.NumberFormat` for money display does not apply here.

## [Phase 2.3] — Currency Utility
**Date:** 2026-06-09
**Files:**
- `src/lib/utils/currency.ts` (created)
- `src/lib/utils/currency.test.ts` (created)
- `TODO.md` (subphase 2.3 marked `[x]`)

### What was built
Three narrow-purpose currency functions that form the strict boundary between the integer-cents domain used for all internal arithmetic and the decimal/string domain used for user display and form input. A 32-test suite covering pt-PT/EUR locale formatting, display conversion, form input conversion, and four IEEE 754 edge cases.

### Technical decisions
- **`formatCurrency` uses `Intl.NumberFormat` — the only sanctioned path for currency display:** All other `Intl.NumberFormat` and `toLocaleString` usages in the codebase are banned by the Reviewer rules. This function is the single exception and the single source of truth for formatted money strings. `cents / 100` inside this function is display-only — the result goes directly into the formatter and is never stored.
- **pt-PT locale uses U+00A0 (non-breaking space) as both the thousands separator and the gap between number and symbol:** This is a ICU locale quirk, not a regular space. All test assertions use the explicit `' '` constant (`NBSP`) to prevent invisible test failures from visually-identical-but-wrong space characters. Discovered by probing codepoints before writing tests.
- **`decimalToCents` uses `decimal.js` with `String(value)` construction — not `Math.round(value * 100)`:** `Math.round(value * 100)` produces wrong results for certain 3-decimal-place inputs due to IEEE 754 binary representation: `Math.round(1.005 * 100) = 100` (wrong) and `Math.round(1.015 * 100) = 101` (wrong). `new Decimal(String(value)).times(100).toDecimalPlaces(0)` avoids this by: (1) converting the float to its shortest decimal string representation via `String()`, which recovers the intended value; (2) performing all arithmetic in Decimal.js's arbitrary-precision decimal engine. The function is "for form input conversion only" — caller guarantees at most 2 decimal places.
- **`String(value)` over `new Decimal(value)` for Decimal.js construction:** `new Decimal(1.005)` would capture the IEEE 754 approximation `1.004999…` because the constructor receives the already-imprecise float. `new Decimal(String(1.005))` first recovers `"1.005"` (JavaScript's shortest-round-trip decimal representation) and constructs an exact Decimal from that string. This is the only path that produces a provably correct result.
- **`centsToDecimal` returns a raw `number` (float), not a string:** It is explicitly "for display only". Its callers are `formatCurrency` (which immediately formats it) and controlled form inputs (which display it as a read-only string). Returning a float avoids forcing callers to parse a string back to a number for the form initial-value prop.
- **No `Number.toFixed()`, no `parseFloat` anywhere in the implementation:** Both are banned by the Reviewer rules for currency logic. The one case where `toFixed` might seem natural (`centsToDecimal`) is avoided by returning the raw float directly. `decimalToCents` uses Decimal.js, which has its own `toFixed`-equivalent that operates on arbitrary-precision Decimals, not on IEEE 754 floats.

### Security / invariants enforced
- `decimalToCents` is the only inbound conversion point from user-supplied decimal values to integer cents. Any other path that multiplies a float by 100 and stores the result is a bug.
- `formatCurrency` is the only outbound formatting point for money strings. Calling `Intl.NumberFormat` directly anywhere else in the codebase is a Reviewer violation.
- `centsToDecimal` output is explicitly documented as unsafe for arithmetic — the JSDoc names every permitted use.

### Known limitations / deferred work
- `decimalToCents` accepts `number` per the spec signature. If a caller passes a value that is already the result of float arithmetic (e.g., `0.1 + 0.2 = 0.30000000000000004`), `String()` will produce `"0.30000000000000004"` and `Decimal.js` will compute 30 (correct), but the input is semantically wrong — it should have been an exact form value. This is a caller responsibility, documented in the JSDoc contract.
- `formatCurrency` locale tests use `toContain` / `toMatch` rather than exact string assertions to avoid brittleness across locales. Only the pt-PT/EUR tests use exact string matching.

## [2.5] Quota Generation & Management — 2026-06-10

### What was built
Seven server actions in `src/app/actions/quotas.ts`:
- `generateMonthlyQuotas(buildingId, budgetId, month, year)` — GESTOR-only; requires APPROVED budget; divides `total_amount_cents / 12` and `reserve_amount_cents / 12` via integer `Math.round`; calls `calculateUnitQuota`/`calculateReserve` per active unit; assigns rounding remainder to the highest-permilagem unit; upserts with `onConflict: "unit_id,due_date", ignoreDuplicates: true` (idempotent re-generation); writes to `audit_log`.
- `markQuotaPaid(quotaId, buildingId, paymentMethod, reference?)` — GESTOR-only; cross-tenant guard via `units!inner(building_id)`; inserts `payments` row with `amount_cents + reserve_cents`; updates quota `status → PAID`, sets `paid_at`.
- `bulkMarkQuotaPaid(quotaIds[], buildingId, paymentMethod, reference?)` — sequential loop over `markQuotaPaid`; returns `{ processed, failed }`.
- `markQuotaOverdue(quotaId, buildingId)` — GESTOR-only; cross-tenant guard; enforces PENDING→OVERDUE transition.
- `waiveQuota(quotaId, buildingId)` — GESTOR-only; cross-tenant guard; enforces {PENDING,OVERDUE}→WAIVED transition.
- `getQuotasForMonth(buildingId, month, year)` — session guard (no role check); joins units; returns `QuotaWithUnit[]`.
- `getMyQuotas(year)` — Condómino read; **no buildingId parameter**; scoped exclusively to `unit_ownership.owner_user_id = session.user.id AND ended_at IS NULL`; returns `MyQuota[]` spanning all buildings/units the caller owns.

`src/components/charts/QuotaStatusChart.tsx` — Recharts PieChart donut; `innerRadius={60}`, `outerRadius={80}`, `paddingAngle={2}`; center label via absolute-positioned div overlay (not SVG text — Tailwind classes unreliable on SVG); design system colors (PAID=#10b981, OVERDUE=#ef4444, PENDING=#f59e0b, WAIVED=#71717a); filters zero-count segments; empty state when total=0.

`src/app/(dashboard)/dashboard/financials/quotas/page.tsx` + `_components/QuotasPageClient.tsx` — GESTOR dashboard; month/year selector; "Gerar Quotas" button triggers `generateMonthlyQuotas` (auto-fetches approved budget for the selected year); status-filter tab bar; `<QuotaStatusChart>` donut; data table with checkboxes; bulk-pay panel (appears when ≥1 eligible row selected); per-row actions (Em Atraso, Isentar).

`src/app/(dashboard)/my-building/payments/page.tsx` + `_components/PaymentsPageClient.tsx` — Condómino view; year selector; summary cards (em dívida / pago este ano); per-building grouped tables showing period, quota, reserve, total, status badge, payment date; data sourced exclusively from `getMyQuotas` — no cross-tenant exposure possible.

### Technical decisions
- **`getMyQuotas` has no buildingId parameter.** The user cannot pass a building they don't own; data is filtered server-side by `owner_user_id`. This is stronger isolation than a buildingId check would provide.
- **Bulk-pay is sequential, not parallel.** `Promise.all` would create concurrent Supabase writes per quota; sequential iteration is safer for audit_log ordering and avoids hitting rate limits.
- **Idempotent quota generation** via Supabase `upsert` with `ignoreDuplicates: true`. Re-generating the same month does not duplicate or error; it silently skips existing rows. The `generated` / `skipped` counts in the return value inform the UI.
- **Rounding remainder on highest-permilagem unit.** After `Math.round(total / 12)` × all units, the sum may differ from `total / 12` (integer drift). The difference is added to the unit with the highest `permilagem`, ensuring collected = budget exactly.
- **Status transition enforcement.** DB trigger (from Phase 2.1 schema) blocks invalid transitions. Server actions therefore don't duplicate the state-machine logic; they trust the DB to reject invalid updates and surface the error.

### Invariants enforced
- All monetary values: integer cents only. No `parseFloat`, `toFixed`, or float arithmetic anywhere in the quota pipeline.
- `getMyQuotas`: scope = `owner_user_id = session.user.id AND ended_at IS NULL`. Callers cannot see another user's quotas.
- `generateMonthlyQuotas`: APPROVED budget required before generation. Rejects with error if budget is DRAFT.
- `markQuotaPaid` / `markQuotaOverdue` / `waiveQuota`: cross-tenant guard on all mutations — fetch record with `units!inner(building_id).eq("building_id", buildingId)` before any write.
- Every mutation writes to `audit_log`.

### Known limitations / deferred work
- `markQuotaPaid` inline (single quota from the table row) is done via bulk-pay with one item selected. A dedicated single-pay flow with a modal (payment method + reference) is deferred.
- `notifyQuotaOverdue` email integration (TODO.md Phase 2.5 note) is deferred to Phase 4.
- Condómino payments page groups by building; if a user owns multiple units in the same building, all appear under the same building heading, differentiated by `unit_identifier`.

This prevents pre-approval disclosure of invoice content, consistent with the expense transparency rule in the same migration.

- GESTOR full access is scoped exclusively to buildings they appear in `user_building_roles` with role `'GESTOR'`.

## [Phase 4.1] — Database: Notification Schema (Migration 005)
**Date:** 2026-06-10
**Files:**
- `supabase/migrations/20260610000005_notifications_schema.sql` (created)

### What was built
Notification persistence layer: three new enum types (`notification_event_enum`, `notification_channel_enum`, `notification_delivery_status_enum`), two new tables (`notifications`, `notification_preferences`), two trigger functions (`guard_notification_immutable_columns`, `set_notification_preferences_updated_at`), seven indexes, and full RLS policy coverage.

### Technical decisions
- **One row per channel per delivery attempt:** Rather than a single `notifications` row with a channels array, each channel produces its own row. This gives precise per-channel delivery status, retry semantics, and individual `sent_at` timestamps without JSONB complexity.
- **INSERT restricted to service role on `notifications`:** No INSERT policy for authenticated users — the service role (used in Edge Functions and server actions with `createServerSupabaseClient()`) bypasses RLS entirely. This enforces that only server-side logic can produce notification rows; clients can never fabricate notifications.
- **`guard_notification_immutable_columns` trigger:** The RLS UPDATE policy only restricts *which rows* a recipient can update, not *which columns*. The trigger raises an exception if any column other than `delivery_status` or `sent_at` is changed, hardening data integrity beyond what RLS alone can express.
- **`notification_preferences` composite PK on `(user_id, building_id)`:** One preference row per user-building membership, matching the `user_building_roles` join pattern. Enables O(1) lookup during notification dispatch in Phase 4.3 trigger functions.
- **`sms_enabled` defaults `true`:** All three channels default to enabled per spec; individual users opt out via the Phase 9.3 settings UI. Phase 4.3 trigger functions will gate on these flags before inserting delivery rows.
- **`notification_preferences_self_insert` WITH CHECK includes building membership:** Prevents a user from creating a preferences row for a building they have no role in, which would otherwise allow building-ID enumeration through INSERT errors.
- **`idx_notifications_recipient_created_at` composite index:** The bell dropdown (Phase 4.4) queries `ORDER BY created_at DESC LIMIT N` filtered by `recipient_user_id` — this composite covers both predicates with a single index scan.

### Security / invariants enforced
- RLS enabled on both tables; all policies follow `{table}_{role/self}_{action}` naming convention.
- `notifications.recipient_user_id` FK uses `ON DELETE RESTRICT` — profile deletion must not silently purge notification history; GDPR erasure (Phase 9.1) anonymises the profile row.
- `notification_preferences` FKs use `ON DELETE CASCADE` — deleting a building or profile cleans up orphaned preference rows automatically.
- Immutable-column trigger prevents recipients from tampering with `building_id`, `payload`, `event_type`, or `channel` on their own notifications.

### Known limitations / deferred work
- No deduplication constraint on `notifications` (e.g. UNIQUE on `(recipient_user_id, event_type, channel, DATE(created_at))`). The overdue-quota-sweep Edge Function (Phase 4.3) will query PENDING rows before inserting to avoid duplicates at the application layer.
- `PUSH` channel is schema-complete but has no provider adapter until Phase 4.2 is extended.
- `notification_preferences` rows are not seeded automatically on user sign-up; the Phase 9.4 onboarding wizard or a server action using `createServerSupabaseClient()` must upsert the default row on membership creation.

Each function returns early on `!data`, so they are safe no-ops until those phases complete.
- **`payload as unknown as Json` cast:** The Supabase JS stub types all insert fields as `Json`. The `payload` helpers accept `Record<string, unknown>` for flexibility; the intermediate `unknown` cast is the standard TypeScript pattern for narrowing between two incompatible-but-correct types without using `any`.

- Edge Function verifies `Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>` — rejects all other callers with 401.

## [Phase 5.1] — Database: Assembly Schema (Migration 006)
**Date:** 2026-06-10
**Files:**
- `supabase/migrations/20260610000006_assemblies_schema.sql` (created)

### What was built
Full PostgreSQL schema for the Assembly & Digital Voting Hub: five tables (`assemblies`, `agenda_items`, `votes`, `vote_proxies`, `atas`), five enum types, four trigger functions, eleven indexes, and a complete set of RLS policies covering GESTOR and Condómino access patterns for all tables.

### Technical decisions
- **`quorum_required NUMERIC(5,2)` instead of INT cents:** Quorum is a percentage (e.g. 50.01%), not a monetary value, so the DBA integer-cents mandate does not apply. `NUMERIC(5,2)` can represent any legally meaningful Portuguese quorum threshold (simple majority 50.01%, qualified two-thirds 66.67%) with the required decimal precision. A CHECK constraint bounds the value to (0, 100].
- **`weighted_permilagem INT` snapshot on `votes`:** Rather than joining to `units.permilagem` at tally time, the unit's permilagem is snapshotted into the vote row at `cast_at`. This ensures that retroactive permilagem amendments (ownership transfers, rebalancing) cannot alter the legally binding vote tally — critical for audit integrity.
- **`DEFERRABLE INITIALLY DEFERRED` on `agenda_items(assembly_id, order_index)`:** The `reorderAgendaItems()` server action (Phase 5.2) swaps multiple `order_index` values in a single transaction. A non-deferrable unique constraint would raise a violation mid-transaction. Deferring until commit allows all rows to be updated atomically before the constraint is evaluated.
- **Four DB-level trigger guards:** Status transition triggers on `assemblies` and `agenda_items` enforce lifecycle order (e.g. CONCLUDED cannot revert to IN_PROGRESS). `guard_vote_immutable` aborts any UPDATE on `votes`. `check_vote_open_state` validates assembly=IN_PROGRESS and item=OPEN at INSERT time. These duplicate the Phase 5.2 server-action checks to provide defence-in-depth against direct SQL, Edge Function bugs, or service-role bypasses.
- **No `building_id` on `agenda_items`, `votes`, or `vote_proxies`:** These tables are scoped to their parent assembly, which carries the `building_id`. Denormalising `building_id` into every descendant table would create update anomalies if an assembly were moved. RLS policies access `building_id` via JOIN through `assemblies` — this is the correct normalised pattern used consistently across the migration.
- **Votes INSERT RLS — app-layer delegation for proxy check:** The proxy ownership chain (grantor → proxy unit → active unit_ownership) is complex to validate entirely in RLS without expensive multi-hop subqueries on every INSERT. The policy enforces the minimum tenant-isolation invariant (`voter_user_id = auth.uid()` and unit in caller's building). The full proxy + unit ownership + assembly-state validation is delegated to the `castVote()` server action running under the service role.
- **`vote_proxies_condomino_delete`:** Condóminos may revoke their own proxy delegation before the assembly starts. Including a DELETE policy allows the `revokeProxy()` server action (Phase 5.2) to run under the authenticated role rather than requiring a service-role client for this user-initiated action.

### Security / invariants enforced
- `votes` has no UPDATE RLS policy AND a `guard_vote_immutable` BEFORE UPDATE trigger — two independent layers prevent vote tampering by any role including service role.
- `check_vote_open_state` trigger prevents votes from being recorded against closed or not-yet-opened agenda items at the DB level.
- Assembly status transitions are strictly ordered; no backward or skip transitions are possible.
- Condóminos cannot see DRAFT assemblies or their agenda items by querying child tables directly — the assembly status filter is re-applied in the `agenda_items_condomino_select` and `atas_condomino_select_finalized` policies.
- `vote_proxies_condomino_insert` verifies active ownership (`ended_at IS NULL`) at the DB level; expired/transferred ownership cannot be used to grant a proxy.
- All trigger functions use `SECURITY DEFINER SET search_path = public` to prevent search-path injection attacks.

### Known limitations / deferred work

### What was built

### Technical decisions
- **`castVote` without `buildingId` parameter:** Building scope is derived server-side from the agenda item's assembly FK chain — no building ID is trusted from the caller. This prevents a malicious client from supplying a different building ID to bypass the cross-tenant guard.
- **`castVote` proxy chain resolution:** Direct ownership is checked first (cheaper query). Only if that fails is the proxy table queried, then the proxy target's ownership is verified. This short-circuits the happy path with a single DB round-trip.
- **`reorderAgendaItems` two-phase offset strategy:** Each Supabase JS call is a separate HTTP request / DB transaction, so the DEFERRABLE INITIALLY DEFERRED constraint on `agenda_items(assembly_id, order_index)` cannot be leveraged across calls. Phase 1 shifts all indices up by 100,000 to clear the target range; Phase 2 writes the final indices. OFFSET=100,000 safely exceeds any realistic agenda item count.
- **`upsertAta` lazy creation:** The ata row is created on first save rather than on assembly creation, avoiding orphan rows for assemblies that never reach the ata-writing stage (e.g. cancelled drafts).
- **`finalizeAta` fires `notifyAssemblyScheduled`:** Per the Phase 5.2 TODO spec, the existing `ASSEMBLY_SCHEDULED` notification event is reused to notify all building members when the ata is published. No new event type is needed.
- **Notification calls use `void …catch`:** Notification failures are logged but never cause the primary action to return an error. This mirrors the pattern established in Phase 4.3 and ensures UX reliability under transient email-provider outages.
- **`updateAssembly` typed patch object:** Rather than `Record<string, unknown>` (which Supabase's generated types reject), the patch is typed as `{ scheduled_at?: string; quorum_required?: number; location?: string | null }`. This allows Supabase to type-check the `.update()` call at compile time and prevents accidentally writing unrecognised column names.
- **`transitionAssemblyStatus` surfaces DB trigger error directly:** The DB trigger message for illegal transitions (e.g. CONCLUDED → PUBLISHED) is informative and already safe to show the caller. Passing it through avoids duplicating the transition matrix in application code.

### Security / invariants enforced
- All GESTOR-only actions call `requireRole(..., ["GESTOR"])` before any DB mutation.
- `castVote` derives `buildingId` from the server-side assembly record — never from the client.
- `grantProxy` and `revokeProxy` verify active unit ownership (`ended_at IS NULL`) before inserting or deleting proxy records; they also confirm assembly is not yet IN_PROGRESS.
- `updateAssembly` blocks edits once the assembly is IN_PROGRESS/CONCLUDED/ARCHIVED — draft integrity is preserved.
- `finalizeAta` requires assembly to be CONCLUDED and the ata to exist in DRAFT state; double-finalisation is blocked.
- `audit_log` entries are written for all state-changing operations: `create_assembly`, `update_assembly`, `transition_assembly_status`, `finalize_ata`.

### Known limitations / deferred work
- `reorderAgendaItems` issues 2×N sequential Supabase calls; for very large agendas a Postgres RPC would be more efficient. Deferred until profiling warrants it.
- No `deleteAgendaItem` action — deferred to Phase 5.3 if the UI requires it.

### What was built
A GET route handler at `/api/assemblies/[id]/ata/export` that renders a formal A4 PDF of a finalized assembly ata and streams it as an attachment. The PDF includes: building header (name, address, NIF), assembly metadata (type, date, location, quorum), ordered agenda items with vote tallies (permilagem for FAVOR/ABSTAIN/CONTRA), the ata body text parsed from Tiptap HTML, and a signature block (Presidente da Mesa / Secretário/a). The PDF template is defined as a React component in `AtaPdfDocument.tsx` using `@react-pdf/renderer` primitives.

### Technical decisions
- **`@react-pdf/renderer` in a Route Handler (not a Server Action):** Route handlers return a `Response` object, making it straightforward to set `Content-Type: application/pdf` and `Content-Disposition: attachment`. Server actions cannot return binary streams. The route uses the Node.js runtime (default for App Router route files) — not the Edge runtime — because @react-pdf/renderer depends on Node.js built-ins via pdfkit.
- **`serverExternalPackages: ["@react-pdf/renderer"]` in next.config.ts:** Prevents Next.js's webpack bundler from trying to analyse @react-pdf/renderer (which would fail because pdfkit uses `fs`, `zlib`, and other Node.js built-ins). Marking it external causes it to be loaded from node_modules at runtime instead.
- **Separate `AtaPdfDocument.tsx` for the PDF component:** The route handler (`route.ts`) uses `createElement(AtaPdfDocument, props)` so it doesn't need JSX and can stay as `.ts`. The React component with JSX is isolated in `.tsx`. This separates concerns: the route handles auth/data fetching, the component handles rendering.
- **HTML → block parser via regex (no extra dependency):** Tiptap's StarterKit produces predictable block-level HTML (`h1–h3`, `p`, `ul/ol > li`). A regex walk over `/<(h1|h2|h3|p|ul|ol)…>…<\/tag>/gi` extracts blocks without needing a DOM parser or additional package. Inline tags (`strong`, `em`) are stripped to plain text since @react-pdf/renderer requires nested `Text` components for inline styles — complexity not warranted for a formal document export.
- **Single `.in()` vote query instead of N per-item queries:** All votes for voting-enabled agenda items are fetched with a single `.in("agenda_item_id", votingItemIds)` Supabase call and aggregated in JS. This mirrors the pattern that `getVoteTally` in the server actions uses, and avoids N+1 database round-trips.
- **`new Uint8Array(buffer)` for the Response body:** `renderToBuffer` returns a Node.js `Buffer`. Next.js 16's `NextResponse` constructor type is based on the Web API `Response` which expects `BodyInit` (including `ArrayBufferView`). `Uint8Array` is a concrete `ArrayBufferView` accepted by TypeScript's Web API types, while `Buffer<ArrayBufferLike>` is not (type narrowing issue). Converting via `new Uint8Array(buffer)` is a zero-copy view of the same memory.
- **Non-GESTORs can only download FINALIZED atas:** The route enforces this server-side: if `ata.status !== "FINALIZED"` and the caller is not a GESTOR, it returns HTTP 403. The AtaTab UI only renders the export button when `isFinalized === true`, but the route guard is the authoritative control.
- **Human-readable filename:** The attachment filename is `ata-{ordinaria|extraordinaria}-{YYYY-MM-DD}.pdf`, derived from assembly type and date. Avoids opaque UUID filenames in the user's Downloads folder.

### Security / invariants enforced
- `getServerUser()` (network-verified JWT) is used instead of `getServerSession()` (cookie-only) because this is a read of sensitive building data.
- Tenant isolation: the assembly's `building_id` is read from the DB (not from the URL or request body), then the caller's membership in that building is verified via `user_building_roles` before any ata content is returned.
- Non-GESTORs are blocked from exporting non-FINALIZED atas — ata draft content is not visible to Condóminos until published.

### Known limitations / deferred work
- Inline bold/italic formatting from the ata editor is lost in the PDF (stripped to plain text). A proper inline-style mapper would require recursive HTML parsing and nested `@react-pdf/renderer` Text components. Deferred as a polish item.
- No watermark or "DRAFT" stamp on non-finalized GESTOR exports. Deferred.
- Custom fonts (e.g. a serifed PT Serif for a more formal look) are deferred — using built-in Helvetica avoids font-file hosting concerns.

## [Phase 6.1] — Database: Incident Schema (Migration 007)
**Date:** 2026-06-10
**Files:**
- `supabase/migrations/20260610000007_incidents_schema.sql` (created)

### What was built
Full PostgreSQL schema for the Incident & Ticket Tracking module. Four new tables — `incidents`, `incident_attachments`, `incident_history`, and `supplier_dispatches` — cover the complete lifecycle of a building defect from first report through supplier dispatch to closure. Two custom ENUM types drive the status machine and priority classification. Five trigger functions enforce data integrity at the database layer. Fourteen indexes optimise the primary query patterns (kanban board, timeline, priority filter). Twelve RLS policies enforce multi-tenant isolation and role-gated mutations across all four tables.

### Technical decisions
- **`incident_status_enum` with 6 states (REPORTED → ASSESSED → SUPPLIER_DISPATCHED → IN_PROGRESS → RESOLVED → CLOSED):** Models the real-world kanban flow for a Portuguese condominium: GESTOR triage (REPORTED→ASSESSED), supplier scheduling (ASSESSED→SUPPLIER_DISPATCHED), active work (→IN_PROGRESS), sign-off (→RESOLVED), and archival (→CLOSED). CLOSED is also reachable directly from any state as an escape hatch for false alarms or duplicates.
- **`priority` nullable on `incidents`:** Priority is meaningless on a freshly reported incident — it requires GESTOR assessment. Making it nullable avoids forcing a placeholder value on INSERT and signals clearly that a NULL priority means "not yet assessed", which the Phase 6.3 UI surfaces as a distinct badge state.
- **`incident_history.from_status` nullable:** The initial creation entry written by `reportIncident()` (Phase 6.2) has no prior status. Using NULL for `from_status` on this synthetic row is more honest than inventing a sentinel state (e.g. "NONE") that does not belong in the ENUM.
- **`enforce_max_incident_attachments` uses `FOR UPDATE` lock on the parent incident row:** A pure count check (`SELECT COUNT(*) … WHERE incident_id = …`) is subject to a TOCTOU race where two concurrent INSERT requests both pass the count-4 check and race to create a 6th attachment. Taking an exclusive row lock on the parent `incidents` row before counting serialises concurrent attachment INSERTs within the same transaction window, preventing the race at zero additional complexity.
- **`check_supplier_dispatch_building_scope` trigger (cross-tenant FK guard):** The FK on `supplier_id` only verifies existence; it does not constrain which building the supplier belongs to. Without this trigger a GESTOR could attach a supplier from Building A to an incident in Building B, leaking supplier PII (name, NIF, contact_email) to users in the wrong building. This mirrors the `check_expense_document_building` pattern from migration 004.
- **`incident_history` immutability enforced by trigger:** History rows are the legally authoritative audit trail of each status change. The `guard_incident_history_immutable` trigger always raises on UPDATE; the RLS provides no UPDATE policy as a first line of defence. Both layers are needed because service-role clients skip RLS but not `SECURITY DEFINER` trigger functions.
- **`updated_at` managed by trigger, not application code:** `set_incident_updated_at` stamps the column automatically on every UPDATE. This removes a class of bugs where application code forgets to include `updated_at` in the UPDATE payload, and ensures the column is accurate even for direct-SQL mutations by operators.
- **`supplier_dispatches` allows multiple rows per incident:** Incidents may require rescheduled visits or multiple specialist contractors. A UNIQUE constraint on `incident_id` would prevent this. The Phase 6.3 detail page renders all dispatches in a chronological list.
- **Partial indexes on `unit_id` and `priority`:** Most incidents will have a non-null `unit_id`; the partial index skips the NULLs. The priority partial index covers the CRITICAL priority fast-scan needed by the mass-notification path in `transitionIncident` (Phase 6.2). Partial indexes reduce index size and maintenance cost vs. full-column indexes.

### Security / invariants enforced
- RLS enabled on all 4 tables; no table is accessible without an explicit policy grant.
- `incidents_condomino_insert` verifies `reported_by = auth.uid()` and active unit ownership (`unit_ownership.ended_at IS NULL`) before allowing INSERT, preventing impersonation and cross-unit reporting.
- `incident_history_condomino_insert_reported` permits Condóminos to write only the initial creation entry (`from_status IS NULL AND to_status = 'REPORTED'`); all subsequent transitions require GESTOR role.
- `check_incident_status_transition` fires `BEFORE INSERT OR UPDATE OF status` — enforces the kanban order at DB level regardless of calling role, providing defence-in-depth against application bugs and direct SQL access.
- `guard_incident_history_immutable` fires `BEFORE UPDATE` on `incident_history` — ensures the legal audit trail cannot be retroactively altered, even by service-role clients.

### Known limitations / deferred work
- Priority-must-be-non-NULL-when-status≥ASSESSED consistency is enforced at the application layer (Phase 6.2 `assessIncident` action) rather than by a DB CHECK constraint. A single-field UPDATE could temporarily leave status=ASSESSED with priority=NULL; the history table provides the audit trail. A deferred constraint or a trigger could enforce this strictly if required.
- `supplier_dispatches.quoted_cost_cents` is nullable (cost estimate not always available at dispatch time). Phase 6.3 UI should surface this as "Quote pending" to avoid confusion.
- No scheduled-visit reminder notification is wired at the DB layer; Phase 6.2 will trigger notifications from the application layer on `dispatchSupplier`.

### What was built
Full server-action layer for the Incident & Ticket Tracking module. Five read functions cover the kanban board (`getIncidents`), detail page (`getIncident`, `getIncidentHistory`, `getIncidentAttachments`, `getSupplierDispatches`). ### Technical decisions
- **Three-function split for status mutations:** `assessIncident`, `dispatchSupplier`, and `transitionIncident` each own a distinct slice of the status machine rather than routing everything through a single `transitionIncident`. This is because `assessIncident` must also set the `priority` column atomically with the status change, and `dispatchSupplier` must also INSERT a `supplier_dispatches` row. Merging them into one function would require a complex union-typed parameter signature and conditional branches that obscure the intent of each call site.
- **LEGAL_TRANSITIONS map excludes REPORTED→ASSESSED and ASSESSED→SUPPLIER_DISPATCHED:** `transitionIncident` validates only the moves it is responsible for. Routing REPORTED→ASSESSED or ASSESSED→SUPPLIER_DISPATCHED through `transitionIncident` would silently succeed at the DB level but bypass the side-effects (priority set, dispatch record creation). The map makes this constraint explicit and surfaces a meaningful error if the caller attempts to use the wrong function.
- **GESTOR bypasses unit ownership check in `reportIncident`:** GESTORs are building administrators who may not own any unit. They must be able to report incidents against any unit on behalf of Condóminos. The ownership guard fires only when `callerRole === "CONDÓMINO"`, mirroring the split in the migration 007 RLS policy.
- **`notifyIncidentCritical` reuses `INCIDENT_REPORTED` event type:** The DB `notification_event_enum` only defines `INCIDENT_REPORTED` and `INCIDENT_RESOLVED`. Adding an `INCIDENT_CRITICAL` value would require a new migration, which is disproportionate for a notification payload distinction. Instead, `notifyIncidentCritical` writes to the `notifications` table with `event_type = 'INCIDENT_REPORTED'` and `is_critical: true` in the JSON payload. The Phase 4.4 NotificationContext can branch on this flag for a distinct badge.
- **`notifyIncidentReported` `!inner` join removed:** The original trigger function used `units!inner(identifier)`, which caused PostgREST to return zero rows when `unit_id IS NULL` (common-area incidents). Fixed to a two-step query: fetch incident without units join, then conditionally fetch unit identifier if `unit_id` is present. Common-area incidents now correctly deliver the in-app notification with `unit_identifier: "Área comum"`.
- **`getIncidentAttachments` generates signed URLs at read time:** Signed URLs with a 1-hour expiry are generated in parallel via `createSignedUrl` so the detail page lightbox can use them directly. The alternative (returning raw storage paths and having the client generate URLs via a client-side Supabase call) would require exposing the storage bucket ACL to the browser or adding a separate signed URL route — both more complex than server-side generation.
- **`uploadIncidentAttachment` does a pre-check count before uploading to storage:** The DB trigger (`enforce_max_incident_attachments`) is the authoritative TOCTOU-safe guard. The pre-check at the app layer provides a user-friendly error message before a file is uploaded (avoiding wasted bandwidth on an upload that would be rejected anyway). The DB trigger remains the hard guard for concurrent requests.
- **Storage rollback on DB insert failure:** If the `incident_attachments` INSERT fails after the storage upload succeeds, the orphaned storage object is removed best-effort (`admin.storage.from("incident-media").remove([storagePath])`). This mirrors the pattern in `documents.ts` (`uploadInvoice`).

### Security / invariants enforced
- Every mutation starts with `getServerSession()` + `requireRole()` or `getUserRole()` — no unauthenticated or out-of-building mutation is possible.
- `reportIncident` verifies `reported_by = session.user.id` is stamped server-side — the caller cannot impersonate another reporter.
- `assessIncident`, `dispatchSupplier`, `transitionIncident` fetch `building_id` from the DB (not from the caller) before the `requireRole` check — prevents a Condómino from passing a `buildingId` they manage as GESTOR in another building to elevate their access on the target incident.
- Cross-building supplier scope is checked in `dispatchSupplier` at the app layer (`suppliers.building_id = incident.building_id`) before the INSERT, in addition to the DB trigger guard.
- `uploadIncidentAttachment` blocks uploads to CLOSED incidents — once archived, no new evidence can be added.
- All notification side-effects are `void`/`catch` fire-and-forget — a notification failure never rolls back or blocks the primary mutation.

### Known limitations / deferred work
- `getIncidentHistory` does not resolve `actor_user_id` to a display name — the caller UUID is returned as-is. Phase 6.3 UI can resolve names with a separate profile lookup or by joining in a future enhancement.
- No `deleteIncidentAttachment` action — attachments can be uploaded but not removed. Adding delete requires a separate RLS policy (GESTOR only, or uploader within a time window) and is deferred to Phase 9 hardening.
- `dispatchSupplier` only transitions ASSESSED→SUPPLIER_DISPATCHED. If the GESTOR wants to add a second dispatch to an already-dispatched incident (rescheduled visit), they must first call `transitionIncident` back to IN_PROGRESS or use `dispatchSupplier` directly from IN_PROGRESS — but the current status guard blocks that. A multi-dispatch enhancement is deferred to Phase 6.3 UI feedback.

## [Phase 7.1] — Financial Summary View
**Date:** 2026-06-10
**Files:**
- `supabase/migrations/20260610000008_financial_views.sql` (created)

### What was built
A PostgreSQL view `public.financial_summary` that aggregates four key financial metrics per building per calendar month: `income_cents` (total collected from PAID quotas), `expense_cents` (total from APPROVED + RECONCILED expenses), `reserve_balance_cents` (cumulative running reserve fund balance), and `outstanding_debt_cents` (total owed from OVERDUE quotas). Two supporting indexes were added to cover the view's query patterns. The view is granted to the `authenticated` role for session-key access.

### Technical decisions
- **`SECURITY INVOKER` instead of a custom RLS policy on the view:** PostgreSQL 15+ supports the `security_invoker` view option, which causes the view's internal queries to execute under the calling session's permissions rather than the view owner's. This means the existing RLS policies on `quotas`, `units`, and `expenses` apply automatically — GESTORs see their building's full data, CONDÓMINOs see only their units. No additional `CREATE POLICY` on the view is required, and there is no risk of accidentally bypassing the underlying tenant isolation.
- **Cumulative window function for `reserve_balance_cents`:** A per-month `reserve_collected_month_cents` column is computed in the `joined` CTE, then a `SUM(...) OVER (PARTITION BY building_id ORDER BY month ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` window function produces the running total. This gives the true state of the reserve fund at any point in time, which is far more useful for analytics than a per-month delta. The phase 7.3 dashboard can select the latest-month row to display the current reserve balance without any additional aggregation.
- **CTE-based UNION merge (`all_periods`) over a FULL OUTER JOIN:** A building may have PAID quotas in a month with no expenses, and vice versa. A FULL OUTER JOIN between `monthly_quotas` and `monthly_expenses` would work, but the UNION + LEFT JOIN pattern is more composable if a third source (e.g. manual journal entries) is added in a later phase without restructuring the whole view.
- **`date_trunc('month', ...)::DATE` for the month column:** Produces `YYYY-MM-01` — a clean DATE value that is directly sortable, comparable, and renderable as a chart x-axis label by the Phase 7.2 chart components via standard JavaScript `Date` parsing. Using a full TIMESTAMPTZ would introduce unnecessary timezone conversion overhead on the client.
- **`CREATE INDEX IF NOT EXISTS` guards:** Idempotent index creation prevents errors if migrations are re-applied in local dev environments or repeated via CI. The Supabase migration runner does not deduplicate index creation by default.
- **`GRANT SELECT ON financial_summary TO authenticated`:** Supabase's `authenticated` role is the JWT-verified role used by all session-key client queries. Without this grant, the view is accessible only via the service-role client. GESTORs query the view from Server Actions that may use the session-key client for RLS to apply; granting to `authenticated` ensures both access paths work.

### Security / invariants enforced
- `SECURITY INVOKER` ensures the view never bypasses RLS: any query to `financial_summary` uses the caller's JWT claims.
- `expense_cents` excludes `DRAFT` and `AWAITING_APPROVAL` expenses — only confirmed outflows (`APPROVED`, `RECONCILED`) are surfaced in the financial summary, preventing uncommitted drafts from distorting cash-flow analytics.
- No `building_id` parameter is trusted from user input; the view is filtered by RLS at the PostgreSQL level.
- The view is read-only (a `SELECT`-only `CREATE VIEW`); no INSERT/UPDATE/DELETE paths exist.

### Known limitations / deferred work
- `reserve_balance_cents` tracks only the _collected_ reserve (quota reserve_cents paid), not the _spent_ reserve. There is no mechanism in the current schema to mark an expense as "drawn from reserve" vs. "drawn from operating funds". A proper reserve ledger table would be required for full reserve accounting — deferred to a future phase.
- The view has no concept of a fiscal-year boundary reset for the reserve balance — it is a continuous running total from the first PAID quota in the database. This is intentional for the current analytics use case; a fiscal-year-scoped reset can be added when the accounting module demands it.

## [Phase 8.1] — Database: SuperAdmin Schema (Migration 009)
**Date:** 2026-06-10
**Files:**
- `supabase/migrations/20260610000009_superadmin_schema.sql` *(created)*

### What was built
An append-only audit table `session_log` that records every SuperAdmin impersonation event and privileged platform action (user suspension, gestor assignment/revocation, etc.). The SuperAdmin identity gate itself requires no new DB table — it is enforced via `auth.users.app_metadata.role = 'SUPERADMIN'`, a signed JWT claim set through the Supabase Auth admin API.

### Technical decisions
- **`app_metadata` JWT claim as the SuperAdmin gate:** Supabase's `app_metadata` is server-controlled and cannot be written by the client SDK, making it tamper-proof without needing a separate `superadmins` table. All RLS policies and the upcoming middleware guard read `(auth.jwt() -> 'app_metadata' ->> 'role') = 'SUPERADMIN'` directly.
- **Append-only enforcement via absent UPDATE/DELETE policies:** PostgreSQL RLS denies operations for which no policy exists. By defining only `SELECT` and `INSERT` policies, the table is structurally append-only — no application code can accidentally overwrite or purge audit rows.
- **`INSERT` policy pins `superadmin_user_id = auth.uid()`:** Prevents a SuperAdmin from writing log entries attributed to a different SuperAdmin's identity.
- **`ON DELETE RESTRICT` on profile FKs:** Preserves audit integrity — a profile involved in a `session_log` row cannot be hard-deleted. This intentionally forces the Phase 9.1 GDPR flow to use PII anonymisation rather than row deletion.
- **`ON DELETE SET NULL` on `building_id`:** A building being deleted should not block audit history; the building context is nullable by design and can safely be nulled out.
- **`idx_session_log_occurred_at DESC`:** The dominant access pattern for audit UIs is time-range queries (latest N actions, actions in a date range); a descending index on `occurred_at` makes these plans index-scan rather than seq-scan.

### Security / invariants enforced
- RLS is enabled on `session_log`; no policy exists for anonymous or regular authenticated users.
- SuperAdmin identity is validated via a tamper-proof signed JWT claim (`app_metadata`), not a mutable DB column.
- The table is append-only — no UPDATE or DELETE paths exist at the policy layer.

### Known limitations / deferred work
- `session_log.action` is a free-text `TEXT` column. A future migration could introduce an `action_enum` to enforce a fixed vocabulary of audit event types.
- Cross-tenant `session_log` queries (e.g., "all actions on building X") will be used by Phase 8.3 admin UI; the `idx_session_log_building_id` index is already in place for those joins.

### Security / invariants enforced
- Every exported function is guarded by `requireSuperAdmin()` before any DB access.
- `suspendUser` refuses to act on another SUPERADMIN, validated via the trusted `app_metadata` claim.
- All privileged mutations produce an immutable `session_log` row — audit trail cannot be bypassed because the write happens inside the server action before the function returns.
- `revalidatePath` is called after every mutation to prevent stale cached data from the admin UI.

- `listAllUsers` fetches at most 1 000 users in one page. A paginated variant will be needed when the platform exceeds that scale.
- `revokeGestor` does not update `buildings.owner_gestor_id` — callers must use `assignGestorToBuilding` to transfer ownership before revoking the current owner gestor.
- `suspendUser` bans at the Auth level but does not invalidate in-flight JWTs. Existing access tokens remain valid until they expire (default 1 h). A future hardening step could shorten the JWT expiry or use Supabase's "logout all sessions" admin endpoint.

- `src/app/actions/gdpr.ts` *(created)*

### What was built
A GDPR Article 17 (Right to Erasure) system comprising an immutable audit table `gdpr_deletion_requests` and two server actions: `requestDataDeletion()` (any authenticated user for self, SuperAdmin for any user) and `processDataDeletion()` (SuperAdmin-only). Anonymisation targets `auth.users.email`, `auth.users.user_metadata`, and `profiles.full_name`/`avatar_url`; all financial audit records are preserved.

### Technical decisions
- **Anonymisation over deletion:** GDPR Art. 17 allows anonymisation as an alternative to erasure when retention is required for legitimate legal/financial purposes. Financial records (quotas, payments, expenses, audit_log) contain no PII beyond FK references — anonymising the profile satisfies the regulation while preserving mandatory financial audit trails.
- **`completed_at IS NULL` when status ≠ COMPLETED (CHECK constraint):** The constraint enforces both sides of the invariant — not just that COMPLETED requires a timestamp, but also that non-COMPLETED rows cannot have a timestamp. This prevents silent partial-state bugs if code sets `completed_at` without advancing the status.
- **`ON DELETE RESTRICT` on both FK refs:** Prevents hard-deleting a profile that is the subject of a GDPR request. After anonymisation, the profile row stays in the DB with `full_name = 'REDACTED'` — the FK chain is preserved without referencing real PII.
- **Partial index `WHERE status IN ('PENDING','PROCESSING')`:** The duplicate-guard query in `requestDataDeletion` always scans only active requests. Completed requests (the vast majority over time) fall off the index, keeping it small and fast.
- **Rollback to PENDING on failure:** If Step 2 (auth email anonymisation) or Step 3 (profile anonymisation) fail, the status is reset to PENDING before the error is returned. This makes `processDataDeletion` safely retryable without creating inconsistent half-anonymised state.
- **Deleted email format `{uuid_prefix_8}@deleted.condoflow`:** The 8-char UUID prefix guarantees uniqueness on the `auth.users.email` UNIQUE constraint while making deleted accounts identifiable to operators. Using the UUID (not a sequential counter) avoids correlation attacks.
- **`user_metadata` also anonymised:** The `handle_new_user` trigger copies `full_name` from `auth.users.raw_user_meta_data` to `profiles`. Anonymising only `profiles.full_name` and not `user_metadata` would leave PII in the auth layer accessible to the trigger on re-execution. Both layers are cleared atomically in Step 2.

### Security / invariants enforced
- `requestDataDeletion` guards: authenticated check, self-only restriction for non-SuperAdmins, duplicate-active-request guard.
- `processDataDeletion` throws `UnauthorizedError` for non-SuperAdmins (JWT-verified via `getServerUser()`).
- No DELETE policy on `gdpr_deletion_requests` — compliance evidence is permanent.
- The action is idempotent for COMPLETED requests (returns error, does not re-run anonymisation).

### Known limitations / deferred work
- The TODO spec mentions "phone/NIF nulled" — neither field exists in the current `profiles` schema (only `buildings.fiscal_number`, which belongs to a legal entity). A future migration adding personal contact fields should also add the anonymisation step to `processDataDeletion`.
- `processDataDeletion` does not currently revoke the target user's active sessions after anonymisation. Existing JWTs remain valid until expiry (~1h). A future hardening step can call `supabase.auth.admin.signOut(userId, 'global')` after Step 2.
- No email notification is sent to the user when their request is processed. A Phase 9+ notification trigger could wire this up.

## [Phase 9.2] — Performance & Security Hardening
**Date:** 2026-06-10
**Files:**
- `next.config.ts` *(modified — security headers)*
- `src/middleware.ts` *(modified — auth-route rate limiter)*
- `src/app/api/assemblies/[id]/ata/export/route.ts` *(modified — Zod param validation)*
- `src/app/api/documents/export/[type]/[id]/route.ts` *(modified — Zod param + query validation)*

### What was built
Four hardening changes: (1) HTTP security headers applied to all routes via `next.config.ts`; (2) IP-based rate limiter on auth-related middleware paths; (3) Zod validation on both API route handler entry points; (4) full audit of all server actions and Supabase client usage.

### Technical decisions
- **CSP via `next.config.ts` headers() rather than middleware:** The `headers()` config applies to all routes without per-request overhead. It is the Next.js-idiomatic approach for static header policies. A nonce-based CSP (which requires middleware to inject the nonce) is documented as the next hardening step to eliminate `'unsafe-inline'`.
- **`X-Frame-Options: DENY` + `frame-ancestors 'none'` both set:** `X-Frame-Options` covers older browsers and HTTP/1.1 proxies; `frame-ancestors` is the CSP2 equivalent and takes precedence in modern browsers. Redundancy is intentional.
- **Rate limiter using a module-level Map in middleware:** In a single-process Node.js deployment the Map persists across requests, providing effective protection. In edge deployments each worker instance has an independent window — acceptable because Supabase Auth's built-in throttle is the distributed protection layer. The 5 000-entry prune guard prevents memory exhaustion. `Retry-After: 60` header follows RFC 6585.
- **Zod validation at the top of each route handler, before `getServerUser()`:** Invalid params are rejected with a 400 before the authentication check, preventing malformed UUIDs from reaching the DB query builder (which would throw an obscure PostgREST error). The type guard also prevents the `type` enum from hitting the `default` branch of the switch statement.
- **Query string pre-parsed in the top-level handler and typed as `{ from?: string | undefined; to?: string | undefined }`:** This resolves the `exactOptionalPropertyTypes` conflict without weakening the schema — `undefined` is explicitly allowed in the type signature, and converted to `null` at the `ExpenseReportDocumentProps` boundary.
- **`dateQuerySchema` uses a regex rather than `z.date()`:** The query params arrive as strings; `z.date()` would require a coercion that has edge-case behaviour with timezone offsets. A regex against `YYYY-MM-DD` format is unambiguous and matches the PostgREST date filter contract.

### Security / invariants enforced — audit results
- **Server action guards:** All 12 action files audited. Every exported function starts with `getServerSession()` or `getServerUser()`. `signIn` and `signUp` in `auth.ts` are correctly unguarded (pre-auth entry points) and protected by Zod schema validation + the new middleware rate limiter.
- **Anon-key client for mutations:** `createServerSessionClient` (anon key, respects RLS) is used exclusively in `auth.ts` for Supabase Auth SDK calls (sign in, sign up, sign out, password reset). All data mutations across all other server actions use `createServerSupabaseClient` (service-role key). No violations found.
- **API route handlers:** Both handlers (`/api/assemblies/[id]/ata/export`, `/api/documents/export/[type]/[id]`) now validate all external inputs with Zod before touching the DB.

### Known limitations / deferred work
- `script-src 'unsafe-inline' 'unsafe-eval'` weakens the script-src directive. Tightening requires middleware to inject a per-request `nonce` attribute into `<script>` tags — a next hardening iteration.
- The in-process rate limiter is not distributed. For multi-region or high-traffic deployments, replace the Map with an Upstash Redis or Vercel KV-backed rate limiter.
- The auth callback route `/auth/callback` is also rate-limited by the middleware but does not validate the `code` query param format before passing it to `supabase.auth.exchangeCodeForSession()`. A Zod UUID/PKCE-format check could be added in a future iteration.

### What was built
A per-building notification preferences page at `/dashboard/settings/notifications`. For every building the current user belongs to, a card shows three channel toggles (Email, SMS, Push). ### Technical decisions
- **Optimistic update + revert pattern:** `useState` holds a local copy of channel flags. The row will be created on the first toggle, keeping the action idempotent.
- **Membership guard in `updateNotificationPreferences`:** Before the upsert, a `user_building_roles` lookup verifies the caller belongs to the requested building. This defends against forged `buildingId` values at the action boundary (RLS also enforces this, giving defence-in-depth).
- **Zod validation on `buildingId`:** The action rejects non-UUID `buildingId` values before hitting the DB, consistent with hardening added in Phase 9.2.
- **`force-dynamic` on the server page:** Preferences are user-specific; opt out of static/ISR caching to ensure data freshness.

### Security / invariants enforced
- `getServerSession()` (anon-key JWT path) used for both actions — no service-role escalation needed.
- Building membership verified before every upsert — prevents cross-tenant preference writes.
- Zod validates `buildingId` (UUID format) and `prefs` (three booleans) before any DB interaction.
- RLS `notification_preferences_self_update` policy provides a second enforcement layer server-side.

### Known limitations / deferred work
- Preferences are per-channel (email/SMS/push) rather than per-event-type per-channel. The DB schema supports only per-channel flags (`notification_preferences` has three boolean columns). A future migration adding a `(user_id, building_id, event_type)` table would allow finer-grained control.

### What was built
A three-step building creation wizard at `/dashboard/buildings/new`. Step 1 collects building details (name, address, NIF/NIPC). Step 2 manages the unit list with a live permilagem counter; the "Next" button is disabled until the sum equals exactly 10 000. The three steps (profile insert → mark invitations accepted → insert role rows) run atomically in a single transaction, so there is no window where an invited user exists without their building membership.
- **Existing users handled via `listUsers` + direct upsert:** When `generateLink` fails (user already confirmed), the action falls back to searching the first 1 000 users for a matching email and upserts the role row. No invite email is sent to existing users — they are added silently.
- **`exactOptionalPropertyTypes` compliance:** The wizard builds the invite array with a conditional property assignment (`if (d.unitId) entry.unitId = d.unitId`) to avoid the `string | undefined` vs `?: string` mismatch enforced by the tsconfig flag, consistent with the approach used in Phase 9.2.

- Both server actions start with `getServerSession()` — unauthenticated callers are rejected before any DB access.
- `inviteCondominos` verifies the caller holds the GESTOR role for the target building before issuing any invite or role assignment.

- Service-role client (`createServerSupabaseClient`) used throughout — no anon-key mutations.
- RLS `building_invitations_gestor_all` policy enforces the same membership check at the DB level (defence in depth).

### Known limitations / deferred work
- The `listUsers` fallback for existing users fetches up to 1 000 accounts per invite. For deployments with > 1 000 users this silently fails to match. A dedicated `auth.users`-backed RPC or Supabase's admin email-lookup endpoint (if added in a future SDK release) would scale better.

- The wizard does not collect `full_name` for invited new users; the invited user signs up with an empty name and must update it in their profile settings.

## [Hotfix] — `getQuotasForMonth` readable by any authenticated user (missing role check)
**Date:** 2026-06-11
**Files:**
- `src/app/actions/quotas.ts` (modified)

### Root cause
`getQuotasForMonth` — the GESTOR-side read that returns quotas for **every unit** of a building — only checked for an authenticated session, unlike its sibling mutations (`markQuotaPaid`, `markQuotaOverdue`, `waiveQuota`, `generateMonthlyQuotas`), which all call `requireRole(..., ["GESTOR"])`. Since Next.js server actions are directly invocable from the client and the query runs through the admin Supabase client (bypassing RLS), any authenticated user — a CONDÓMINO, or a user from another building — could pass an arbitrary `buildingId` and read all residents' quota amounts and payment statuses.

### Fix
- Added the standard `requireRole(session, buildingId, ["GESTOR"])` guard to `getQuotasForMonth`; unauthorized callers now get `[]` (consistent with the unauthenticated path). CONDÓMINO reads remain on `getMyQuotas`, which is identity-scoped via `unit_ownership` and takes no `buildingId` parameter.
